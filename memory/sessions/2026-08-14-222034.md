## What was built

deployable apps:

| Module | Ports (rest-automation / spring) | Role |
|---|---|---|
| `order-manager` | 8081 / 8091 | Order intake REST, CQRS read model, outbox relay |
| `order-steward` | 8082 / 8092 | Fulfillment lifecycle graph, SoR dispatch, dispatch-window scheduler, outbox relay |
| `order-acknowledge` | (none) | Stateless: `sor.ack` → `fulfillment.ack` |
| `order-sor-mock` | (none) | Stands in for the SoR; acks three milestones |

The steward's lifecycle is the four-checkpoint suspend/resume graph `fulfillment-lifecycle`
(Redis-backed via `minigraph-state-redis`): VALIDATED → SCHEDULED → DISPATCHED → SOR_VALIDATED
→ SOR_PREPROCESSED → SETTLED, with `failed` / `rejected` terminals. Transactional outbox in
both DB-owning apps, no inbox table, per-transition `fulfillment.status` events.

## Verified end-to-end

Live drive against kafka-standalone, redis-standalone and seeded `manager` / `steward` DBs:

1. **Happy path** — full six-transition lifecycle → `SETTLED`, order rolled up to `COMPLETED`.
2. **Fail milestone** — SoR fails `preprocessed` → `FAILED` with reason `sor_preprocess`, order `FAILED`.
3. **Duplicate / stale ack** — replaying two acks against an already-`SETTLED` fulfillment changed
   nothing (events 6→6, line_history 6→6, order `COMPLETED/2` unchanged).

Final state: both outboxes fully drained, zero dead-lettered messages, no application errors.

## Durable findings (framework contracts, learned the hard way)

1. **`simple.kafka.notification` takes `topic` and `cid` as HEADERS, body = the payload.**
   There is no record-key parameter — the business correlation-id rides as a Kafka *header*
   (`KafkaHeaders.CORRELATION_ID` = `cid`), which is what the flow adapter turns back into
   `model.cid`. A `{topic, key, body}` wrapper map silently publishes nothing: the missing-topic
   `IllegalArgumentException` is swallowed by fire-and-forget `po.send`, so the caller logs
   success while the topic stays empty. Both relays now publish with `po.request(...).get()` so a
   rejected message is never marked `sent_at`.

2. **A `jsonb` column read through r2dbc is NOT a Map.** It arrives as a driver `Json` wrapper
   that serializes as `{"value":[<byte ints>]}` — the payload reaches Kafka as an array of
   character codes. Select `payload::text` and parse, rather than trusting the column type.

3. **Statements inside one `PgTransactionStatement` do not reliably see each other's writes.**
   The manager's order rollup read `routing_map.line_status` that a sibling statement had just
   set, got the stale value, and silently skipped the rollup (the UPDATE still matched, so
   `status_version` incremented while `order_status` did not). Rewritten to evaluate the current
   line from a bound `:to_state` and read only the *other* lines from the table.

4. **`graph.executor` can only be driven from inside an Event Script flow** — it resolves a live
   flow instance from the `instance` header and rejects anything else. A scheduled job therefore
   cannot call it directly; the dispatch-window tick publishes to `fulfillment.tick` and a flow
   (`steward-tick-flow`) drives the graph. This replaced an HTTP call back into the same JVM.

5. **`mini-scheduler` requires `resolver` on every job** (`JobLoader.loadConfig` fails the entry
   without it, logging only "Invalid job entry#N"), and the cron interval must exceed 10s because
   deferred start adds a 0–9s jitter.

6. **With `rest-spring-4` on the classpath an app binds TWO ports** — `rest.server.port`
   (rest-automation: `rest.yaml`, flows, `/api/graph/...`) and `server.port` (Spring). Setting
   both to the same value fails at startup with "port already in use" against itself.

7. **The top-level `flow:` key in a kafka-flow-adapter binding takes a BARE flow id.** The
   `flow://` prefix belongs only to second-level routing rules under `flows:`.

8. **Depend on `reactive-postgres` alone for r2dbc** — it already declares
   `spring-boot-starter-data-r2dbc` *with* the `spring-boot-starter-logging` / `logback-classic`
   exclusions. Redeclaring the starter in an app pom reintroduces
   "log4j-slf4j2-impl cannot be present with log4j-to-slf4j" and the app will not boot.

9. **Suspend/resume consume-on-read makes a stale ack dangerous unless the graph guards for it.**
   Once a lifecycle settles, its Redis record is gone, so a replayed ack starts a FRESH run. The
   fresh-path guard must probe a field only a genuine *request* carries (the payload) — probing
   `fulfillment_id`, which acks also carry, let a stale ack fall through and rewrite a SETTLED
   fulfillment to REJECTED. The guard now routes to a `NOOP` terminal that `v1.txn.record.status`
   short-circuits on.

## Assumptions recorded

- `fulfillment.tick` (+ `.dlq`) added beyond the spec's topic list, to carry the dispatch-window

## Addendum — boot scripts (same session)

Added repeatable provisioning, and shut the apps down.

- `examples/order-system/boot-infra-dependencies.sh` — PostgreSQL (Homebrew service), plus
  redis-standalone and kafka-standalone as plain java processes from `helpers/`. Supports
  `--status` and `--stop`. Builds a helper jar if it is missing and reads the framework version
  from the root pom rather than pinning it.
- `<module>/boot-dependencies.sh` × 4 — each project provisions what it owns: its database
  (dropped, recreated from an in-repo `db/*.sql`), its Kafka topics + DLQs, and for the steward
  the Redis `graph:*` keys. **Delete always precedes create.**
- `node/recreate-topics.mjs` + `package.json` — kafkajs topic admin (delete, poll until really
  gone, recreate), following the `examples/kafka-demo/node` precedent. `node_modules` gitignored.
- The two schema files were copied from `~/tmp/tutorials` into `order-manager/db/manager.sql` and
  `order-steward/db/steward.sql` so the scripts are self-contained.
- `README.md` documenting the two-layer setup, the topic-ownership rule and the lifecycle.

**Ownership rule adopted:** a project recreates only the topics it CONSUMES. A topic it merely
publishes to is owned by whichever project reads it, so two boot scripts can never delete each
other's data.

Verified: infra script from cold; all four project scripts; a second run proving deletion really
happens (a seeded sentinel row and two seeded `graph:*` keys were both gone); then a full
end-to-end drive on the script-provisioned state — happy path `SETTLED`/`COMPLETED` and a failed
milestone `FAILED`/`FAILED`. Apps shut down afterwards.

**Two portability bugs found and fixed while testing the infra script** (both silent under
`set -euo pipefail`): `sed -n '0,/re/'` is a GNU extension that yields nothing on BSD/macOS, so
the version came back empty and the jar path was wrong; and `pgrep | head` under `pipefail`
returns pgrep's exit 1 when nothing matches, aborting the script on the normal "helper not running
yet" path (needs `|| true`).
